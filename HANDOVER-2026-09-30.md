## 4. NEXT: Resources pagination (Ravi chose option A)

**Endpoint:** `GET /api/dashboard/resources` → `app/main.py:4473` → `app/resources.py` `get_resources().inventory(...)`.

**Why it is slow:** builds per-service detail for ~2M resources only to publish the top 8,000. A rank-first rewrite was
tried and measured **slower (227 s)** — don't repeat it.

**Plan:**
1. **Prototype on real data first** (SQL only, `EXPLAIN (ANALYZE, BUFFERS)`, materialise real results — never
   `count(*)` wrappers). Idea: map resource IDs to **integer keys** (a resource identity table) so aggregation/joins
   hash ints, not long text IDs, across millions of rows; build a **per-resource serving table** in the derived
   rebuild (CTAS), keyed by window/subscription.
2. Endpoint becomes **server-side paged/sorted/filtered** (`page`, `page_size`, `sort`, `q`, filters) with
   parameterised SQL; return `total` and an explicit truncation flag (lesson: no silent limits).
3. Keep the classic UI working (compat response) and add a `/v2` Resources screen with a virtualised TanStack Table
   driven by the paged API.
4. Exactness test: page-union == old full result on a fixture; re-bench → update §12.
**Target:** < 1 s cold, < 300 ms warm per page.

**After that:** Waste (add a pre-normalised `lower(trim(ResourceId))` key column to `resource_presence`, indexed;
one-time rebuild) → then S2.
