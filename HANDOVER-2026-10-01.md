## 2. S5 result — measured, not yet written into `plan.md`

Ran on the copy (D2ds_v5, 2 vCores / 8 GB), from container instances in the VNet as `id-cloudlens`. Python side =
the app's own `ingest_export` path; SQL side = `azure_storage.blob_get(…, NULL::<row type from the file's footer>,
decoder := 'parquet')` through the same header mapping, as one `INSERT … SELECT` per file into the staging-table shape.

| 5.8M-row synthetic month (6 files × 966,667 rows, 1.27 GB Snappy) | Time | Rows/s |
|---|---|---|
| App's Python loader (1 vCPU / 1.7 GB container, peak RSS 944 MB) | 938 s | 6,180 |
| In-database, 1 session | 456 s | 12,730 |
| In-database, 3 sessions | 284 s | 20,461 |
| In-database, 6 sessions (2 vCores saturate) | 257 s | 22,609 |

- **Real data: identical.** The 13 real months (13 files, 37,242 rows) matched row for row both ways and equal the
  app's `costs` table (in-DB 7.2 s, Python 6.0 s — small files, overhead-bound).
- **Synthetic month: not identical.** 319,818 of 5.8M rows differ, in BilledCost, EffectiveCost, InvoiceCost,
  ListCost, ContractedCost and CostInUsd. **Cause: `azure_storage` 1.10's Parquet decoder drops the minus sign of
  every decimal between −1 and 0** (−0.63279 arrives as 0.63279). Proven on the decoder alone:
  - `spike.py decimals 1` (pyarrow vs decoder, per decimal column of `part_0`): ≈ 5,400 values in (−1, 0) per
    money column; the decoder sees **none**, its (0, 1) bucket is larger by exactly that many; ≤ −1, zero, ≥ 1
    and null counts are identical.
  - `spike.py decimal_types`: declaring the column as `numeric`, `text`, `double precision` or `bytea` all give
    `0.632790…` (bytea shows the ASCII text) — the decoder writes the number as text without the sign, so there is
    **no SQL-side workaround**.
  - Effect on the month: BilledCost 6,138,360.50 → 6,159,843.80 (**+0.35%**). Real exports here simply had no such
    values; a small credit or rounding adjustment would silently become a charge.
- **Verdict (plan §7 S5 step 4, "switch only if correct and at least as fast"): no-go — keep the Python
  byte-mover; transforms stay in SQL.** 2.1–3.7× faster, but wrong. Re-check when `azure_storage` changes:
  `spike.py decimals 1` takes ~2.5 min.
- Also learned (belongs in ADR-6):
  1. The decoder binds by **column position only**; the row type must be built per file from its footer.
  2. Mirror parity: a null text cell is blank to Python (`''`), so SQL must treat it as absent, not NULL. The old
     mirror refused 48,046 rows per file with a null `x_BillingExchangeRate` (fixed in `Transform.present()`).
  3. A restored server has **no managed identity** until re-enabled; `azure_storage` then fails with "insufficient
     arguments provided to blob fetching process" (`blob_list`) and "Failed to create streaming Parquet decoder:
     Unknown error code" (`blob_get`).
  4. On 8 GB, an all-column `GROUP BY` over 11.6M rows with `work_mem = 1GB` + parallel workers took memory to 93%,
     the backend was killed, and crash recovery **emptied the unlogged tables**. Bounded (256 MB, no parallel
     workers) it took 123 s. In-DB transforms in v3 must size `work_mem` per server.
  5. In-DB loading itself is light: memory 18% → 45% (shared buffers filling), CPU ≈ 40% for one session.

## 7. Rules that bite (new; HANDOVER-2026-09-30 §9 still applies)

1. **Never scale a stopped Flexible Server.** Start it, wait for Ready, then scale. Governance stops the test
   server (it did at 00:35 IST, 20 min after it became Memory Optimized).
2. Trust the `is_db_alive` metric, not Resource Health.
3. The PostgreSQL async-operation endpoint (`…/locations/centralindia/azureAsyncOperation/<id>`) means something
   only for an id from a response's `Azure-AsyncOperation` header; any other id returns "Canceled" with
   `startTime` = now.
4. `az postgres flexible-server restore` has no `--sku-name`; an `az rest` PUT with `createMode:
   PointInTimeRestore` and a `sku` restores straight onto another size (that is how the copy landed on D2ds_v5).
   Then enable the identity and re-grant its roles.
5. On 8 GB servers bound `work_mem` for big aggregates; a crash empties UNLOGGED tables (the app's staging tables
   are unlogged).
6. The PC sleeps: a local watcher stalled from 03:44 to 09:17. For long runs keep it awake
   (`SetThreadExecutionState`, see `keep-awake.ps1`); the container instance keeps going either way.
7. PowerShell: variable names are case-insensitive (`$script` is `$Script`); a hex literal ≥ `0x80000000` is a
   negative Int32 (use `[uint32]2147483649`); `az` is `az.cmd`, so a URL containing `&` gets split — use
   `Invoke-RestMethod` with `az account get-access-token`.
