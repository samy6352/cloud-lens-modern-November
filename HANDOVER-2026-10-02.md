## 3. Findings that save time

- **A 503 "Committed source data is still being prepared" is not an outage.** It means `data_rollup_dirty` has `windows: null`
  (full derived rebuild pending); `/readyz` still says ready. A restart after code changes can start a full rebuild: presence
  (~15 min), billing_rollup (~7 min per month), commitment_benefits, resource_tags, costs_fx_rollup, … **~2 h in all** on this box.
  It clears when `select value from meta where key='data_rollup_dirty'` shows `"windows": []`. Check with `psql` using
  `PGPASSWORD` from `.env` (`-w`, or it prompts and hangs).
- **Sampling `pg_stat_activity` while a cold request runs shows which tabs are DB-bound vs live-Azure.** ai-billing and
  billing/opportunities showed almost no DB time: they are live Azure. AKS is DB: one `lower(...) LIKE` group query over the
  presence table, 2.4 s on cold buffers (146k pages), 0.02 s warm. Decided not worth indexing (trigram/expression indexes on a
  2.8M-row table inside the rebuild path for ~4 s on first touch).
- Earlier "opportunities is 10 s DB-bound" was a mis-attribution (the sampled query was AKS's). Don't repeat it.
- Local PostgreSQL service `postgresql-x64-18` was **stopped by an administrator command at 12:39 IST** (not by me, not a crash)
  and could not be started from a non-elevated session (service runs as NetworkService). Ravi restarted it ~16:03.
  If it is down again: `Start-Service postgresql-x64-18` from an elevated PowerShell. Don't work around with `pg_ctl`.
